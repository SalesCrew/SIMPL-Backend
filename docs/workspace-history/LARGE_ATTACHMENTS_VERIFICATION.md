# 500 MB attachments — 2026-08-31

## Implemented

- 500 × 1024 × 1024 bytes per file for card and comment attachments.
- Supabase project `Trello+` (`xqvexzoswhraqicbmckj`): global Storage setting saved at 500 MB; private `card-attachments` bucket and metadata constraint verified at 524288000 bytes. No plan, spend-cap, public-access or RLS changes.
- Applied `20260831162654_large_attachments.sql`; new upload reservations expire after 24 hours.
- Files over 6 MB use the pinned `tus-js-client@4.3.1`, direct Storage hostname and 6-MB chunks. Transient failures retry from the server offset. Tokens are refreshed per request; upload URLs/fingerprints are not persisted.
- Files over 20 MB are opaque downloads, not image previews. Finalization checks authoritative Storage size/type without loading the whole file in the API. Large download blobs are not retained as preview caches.
- App/API changes are local and have not been redeployed to Vercel.

## Verification

- Frontend: 139 tests passed; production build passed.
- Backend: 35 tests passed; TypeScript build passed. A dedicated test asserts that 500-MB finalization never calls Storage download.
- Existing card and comment attachment integration suites passed against the real Supabase project and local API: ownership, private drafts, authenticated access, anonymous denial, deactivation, atomic publication, undo and cleanup.
- Full test transferred **524288000 bytes** using one reusable 6-MB fixture buffer and the same pinned TUS client as the frontend. It recovered a deliberately lost chunk acknowledgement and actual connection interruptions, completed the upload, finalized metadata and published it with a comment.

- All disposable test accounts, cards, comments, completed files and pending upload sessions from successful runs were removed. No user files were deleted; fixtures are generated by the test script.
